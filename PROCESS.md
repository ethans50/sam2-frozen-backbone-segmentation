# Design Process and Rationale

This document records the reasoning behind the design decisions in this repository — why the
architecture, hyperparameters, and evaluation protocol look the way they do — and the measured
values that back each decision. Results themselves are reported in [`README.md`](README.md);
this document explains how those results were arrived at.

## Research Question

How well does a SAM2 image encoder, pretrained on natural images and left entirely unmodified,
transfer to standard multi-class semantic segmentation when only a lightweight decoder is
trained on top of it? And does a decoder trained on one dataset generalize to a different
dataset in a different domain, or does it merely learn a shallow mapping that overfits the
dataset it was trained on? The second question is answered with a cross-dataset evaluation:
a decoder trained exclusively on Cityscapes is evaluated, without any further training, on
CamVid — a dataset with a different camera, different cities, and different class taxonomy.

## Design Principles

### Why SAM2

SAM2 has a mature ecosystem (checkpoints, code, documentation) and ships official checkpoints
across a range of sizes (`tiny` to `large`), which makes it straightforward to compare transfer
performance as encoder capacity changes. It is a standard choice for frozen-backbone transfer
experiments of this kind.

### Why Freeze the Encoder

1. Fully fine-tuning a large pretrained model on a small or mid-sized dataset carries a high
   risk of overfitting and catastrophic forgetting; freezing the encoder is the standard way to
   avoid this in transfer learning.
2. Running the encoder under `torch.no_grad()` avoids storing activations for backpropagation,
   which allows a larger batch size than a fully trainable model would.
3. Because only the decoder is trained, cross-dataset evaluation measures a clean quantity: how
   well the decoder generalizes on top of the encoder's general-purpose representation, rather
   than whether the encoder itself memorized dataset-specific features. This is the central
   question Phase 2 is designed to answer.

### Decoder Design

The decoder takes SAM2's `backbone_fpn` (a list of multi-scale feature maps) as input:

1. Project each scale to a common channel width with a 1x1 convolution.
2. Bilinear-upsample every scale to the resolution of the highest-resolution scale.
3. Concatenate the upsampled features and pass them through two 3x3 convolutions.
4. Apply a final 1x1 convolution to produce `num_classes` output channels.
5. Bilinear-upsample the logits to the input resolution before computing the loss.

No asymmetric or window-based attention mechanisms are used in the decoder — the input images
are standard natural-image aspect ratios with no special structure to exploit, so added
architectural complexity would not be justified here.

### Loss and Evaluation Design

- **Loss**: combined CrossEntropy + Dice. Dice loss is more robust than CrossEntropy alone
  under the class imbalance present in both datasets (large classes such as road/sky versus
  small classes such as pole/pedestrian).
- **Evaluation**: standard mIoU, with per-class IoU also reported separately — identifying
  which classes are weak is itself part of the research question, not an afterthought.
- **The ignore index (void class) is excluded from both the loss and the mIoU computation.**
  Omitting this on either side would distort the reported metric.

## Phase 2 Configuration: Cityscapes and Cross-Dataset Evaluation

### Objective

Scale training data and per-class sample counts substantially using Cityscapes (thousands of
images across 50 cities), while using **CamVid — excluded entirely from decoder training — as
a fully held-out evaluation set**. This is a stricter generalization test than a conventional
train/val/test split within a single dataset. Because training longer or harder can raise an
in-domain metric through overfitting alone, that in-domain number is not treated as the primary
success criterion here. The primary criterion is: **how well does a decoder trained only on
Cityscapes perform, at the category level, on CamVid images it has never seen?**

### Dataset: Cityscapes

Official distribution: fine annotations, 2,975 training images and 500 validation images (the
1,525 test images have no public labels and are reserved for the official evaluation server, so
they are not used here — validation performance is used for model selection instead, with the
final generalization claim coming from the CamVid cross-evaluation below). Labels are decoded
from `gtFine/*_labelIds.png` (34-class `id`) to 19-class `trainId` by importing the official
`labels` table from the `cityscapesscripts` package directly, rather than transcribing it —
this removes any possibility of a transcription error in the mapping.

The decoder trains on the 19-class `trainId` scheme (the standard Cityscapes convention),
which allows Cityscapes val mIoU to be reported as a literature-comparable secondary metric.
The 7-category grouping (flat / construction / object / nature / sky / human / vehicle) is the
official Cityscapes `category` field — not a taxonomy invented for this project — reused as
the common label space for cross-dataset evaluation:

| CamVid11 class | -> category |
|---|---|
| Sky | sky |
| Building | construction |
| Pole | object |
| Road | flat |
| Pavement | flat |
| Tree | nature |
| SignSymbol | object |
| Fence | construction |
| Car | vehicle |
| Pedestrian | human |
| **Bicyclist** | **excluded (ignored in cross-evaluation)** |

**Bicyclist exception**: CamVid's `Bicyclist` class labels a person riding a bicycle as a single
class, without separating person from bicycle. Cityscapes separates these into `rider` (human
category) and `bicycle` (vehicle category). Forcing `Bicyclist` into either category would be an
arbitrary decision with no clear basis, so `Bicyclist` pixels are excluded (ignored) from the
cross-evaluation mIoU computation, and this exclusion is stated explicitly in all reported
results rather than left implicit.

### Model Selection

Phase 1 used `sam2.1-hiera-tiny`. With substantially more training data in Phase 2, a larger
encoder's representational capacity becomes worth using if it fits in the available 8GB of
VRAM. All four SAM2 sizes were benchmarked directly (forward pass only, encoder under
`torch.no_grad()`, at the target resolution and batch size) before choosing:

| Checkpoint | Peak VRAM (forward only) |
|---|---|
| tiny | 0.47GB |
| small | 1.20GB |
| base_plus | 1.37GB |
| large | 1.99GB |

All four fit comfortably within 8GB — because the encoder runs under `no_grad()`, it does not
retain activations for backpropagation, so even the largest checkpoint adds little memory
pressure. `large` was selected to make full use of the larger Phase 2 dataset.

### Resolution

Cityscapes images are natively 2048x1024 (2:1 aspect ratio), unlike CamVid's 4:3. Whether SAM2's
encoder handles non-square input correctly (rather than requiring a square resize, which would
distort the image) was measured directly rather than assumed: 1024x1024, 1024x512, 768x384,
512x256, and 512x1024 were all run successfully, since Hiera's windowed attention adapts to the
input size internally. **1024x512** was chosen — half of the native resolution, aspect ratio
preserved, no distortion and no padding required.

### Training and Evaluation Strategy

Training longer or harder to raise an in-domain metric is not, by itself, evidence of
generalization — it can also be evidence of overfitting. To keep the cross-dataset result
meaningful, four constraints were applied:

1. **Model selection (best checkpoint) uses Cityscapes validation mIoU only.** CamVid is never
   consulted when selecting a checkpoint.
2. **CamVid is used exactly once, at the end, for the cross-dataset evaluation** (reusing the
   label indices already validated in Phase 1) — it is never mixed into training data.
3. If Cityscapes val mIoU were to keep improving while the CamVid cross-evaluation mIoU stayed
   flat or declined, that would be recorded explicitly as evidence of overfitting to the
   Cityscapes domain — the exact failure mode this experiment is designed to detect.
4. Epoch count uses early stopping on Cityscapes val mIoU, with a more generous patience than
   Phase 1, to find a natural convergence point without training long enough to overfit the
   validation set itself.

## Qualitative Error Analysis

The 6 representative samples saved by `eval.py`/`eval_phase2.py` were not sufficient to see a
balanced mix of strong and weak cases (in Phase 1, all 6 happened to be consecutive frames from
the same sequence). `scripts/visualize_cases.py` was added to score every image in each
held-out set individually and select the top/bottom 5 by score:

| File prefix | Set | Size | Per-image score range |
|---|---|---|---|
| `eval_test_best{1-5}_*.png` / `eval_test_worst{1-5}_*.png` | Phase 1, CamVid test (11-class) | 168 images | 0.4939 - 0.8348 |
| `cross_eval_best{1-5}_*.png` / `cross_eval_worst{1-5}_*.png` | Phase 2, CamVid cross-evaluation (7-category) | 701 images | 0.3944 - 0.8404 |

**This per-image score differs from the official mIoU reported in `results_phase1.json` /
`results_phase2.json` in two ways, neither of which affects the official metric:**

1. **Scope**: the official metric accumulates a confusion matrix over every pixel in the entire
   held-out set at once (`torchmetrics.MulticlassJaccardIndex(average="macro")`) and averages
   per-class IoU from that. The ranking score here computes a confusion matrix per individual
   image, averaged only over classes that actually appear in that image's ground truth
   (excluding absent classes avoids unfairly penalizing, for example, a frame with no Bicyclist
   pixels with an IoU of zero for that class).
2. **Separation of concerns**: `visualize_cases.py` never writes to or reads from
   `results*.json` — it is a visualization-selection aid only, computed independently of the
   official evaluation scripts. The two code paths do not share state, so this ranking score has
   no way to influence the reported metric.

**Patterns observed in worst-case images:**

- **Thin, repetitive structures (lamp posts, bare tree branches, bollards) are smeared into
  blunt blobs or lost entirely.** This is structural: the decoder's highest-resolution
  prediction grid is SAM2's highest-resolution feature scale (stride 4, i.e. 128x128 at 512
  input — see Decoder Design and the Phase 1 table above), upsampled 4x directly from there.
  Structures thinner than that grid spacing are lost before the final upsample even happens
  (confirmed in `eval_test_worst1/2/4` and `cross_eval_worst4`).
- **Cluttered scenes with several small objects close together score lower.** Adjacent class
  boundaries bleed into each other (e.g. `cross_eval_worst4` shows vehicle/human/object classes
  intermixing), which compounds the resolution limitation above.
- **A pattern specific to the Phase 2 cross-evaluation**: 2 of the 5 worst images
  (`cross_eval_worst1`, `worst2`, consecutive frames from the same gas-station scene) show a
  false positive: the model predicts "vehicle" in an empty, shadowed area under a structure
  where no vehicle exists. This looks like a domain-shift effect rather than the resolution
  limitation above — the model appears to have learned, from Cityscapes road scenes, that "a
  dark mass beneath a roof/structure" correlates with a vehicle, and over-applies that pattern
  to CamVid's different scene layouts. This is a distinct failure mode from the thin-structure
  limitation already known from Phase 1, and only became visible through cross-dataset
  evaluation.
